# Final JSON and image package

This package contains the intersection of events with accepted coordinates,
a validated non-empty causal chain and existing Sentinel imagery. It does not
impose a fixed event count. It is assembled offline from existing pipeline
outputs: no LLM calls, downloads or uploads take place during export.

## Files

```text
release/
  README.md
  package_manifest.json
  data/dataset.json
  images/<event_id>/<product>/day_00_YYYY-MM-DD.tif
  images/<event_id>/<product>/day_00_YYYY-MM-DD.png
  images/<event_id>/worldcover/worldcover_2020.tif
```

`dataset.json` is a dictionary keyed by the country-specific EM-DAT event id.
Image paths use `/` and are relative to that JSON: `../images/...`.
`package_manifest.json` records the event ids, input fingerprints and the size
and SHA-256 of every exported image. Publish only when its `status` is `complete`.
TIFFs remain scientific files; available PNGs are previews, not replacements.

The selection CSV and export report are outside the public package, alongside
the release directory. They include exclusions and context warnings and are for
the research audit, not additional events to upload as part of the dataset.

## Selection

The exporter checks the accepted `position_source`, coordinate ranges, event
date and the actual saved causal steps. It verifies the satellite manifest id,
date, coordinates, 21-day window and bounding box. Image paths must stay within
that event's directory; missing, empty or unrecognized image files are rejected.
Image signatures, file sizes and hashes are checked, not scientific pixel quality.
WorldCover or validity masks alone do not make an event eligible.

Partial collections with real imagery are included by default, preserving
their status and failed sensor-days. `--require-complete` excludes them.
`completed` does not mean all sensors have images on all 21 days: `no_scene`,
`no_data` and `disabled` are resolved slots. A scene can be cloudy and need not
show disaster damage. Only files referenced by selected manifests are packaged.

## Fields

- `disaster_id`, `disaster_type`, `country`, `region`: event identity and EM-DAT classification.
- `latitude`, `longitude`, `position_source`: accepted coordinates and their provenance.
- `event_date`: the saved event start date; the old start/window date fields are not exported.
- `total_deaths`, `total_affected`: EM-DAT counts, not estimates generated by the LLM.
- `total_damage_usd`: original EM-DAT damage in USD; a source column in thousands of USD is multiplied by 1000, not replaced with inflation-adjusted damages.
- `weather_data`: units, pre/post means and the aligned daily series.
- `satellite_data`: actual processing bbox/CRS, availability and product paths.
- `news_data.search_metadata`: successful source groups, counts and filtered final article references.
- `causal_chain`: retained step list plus model/version/validation counters; no duplicate total chain, prompt or raw response.
- `summary`: only `usable_news`, `total_chars`, `news_input_quality`, `event_summary`.

Every unavailable scalar or unavailable data block is the string `"none"`, not
JSON null, NaN, an empty string or a substituted zero. Real numbers stay numeric,
including real zero values. Known empty lists stay `[]`, and known states such
as `no_scene` are not replaced with `"none"`.

### Weather

The retained field name `daily_20_days_series` contains **21 days**, indexed
0 through 20: index 0 is D-10, index 10 is the event date, index 20 is D+10.
Every row has its date, index, `rain_sum`, `snowfall_sum`, `temperature_2m_max`
and `temperature_2m_min`. These are daily accumulations or extrema, not daily
mean temperatures. The pre-event mean uses indices 0-9 and the post-event mean
uses 11-20; the event day is excluded from those two aggregates.

Means are recomputed from the daily values, excluding missing values and known
fill codes. `valid_days` reports the denominator **per variable**. Temperatures
are degrees Celsius and rainfall is mm under the pipeline's existing defaults.
An unknown snowfall unit is `"none"`; units are not invented.

Historical weather records may lack provider/unit metadata. The old NASA POWER
fallback filled unavailable snowfall and missing values with zeros, and used
total corrected precipitation as the rainfall field. Without saved provenance
the exporter cannot distinguish these from observed zeros or recover true
rain-only measurements. Such records produce audit warnings; stored finite
values are preserved, not silently reinterpreted. If a record explicitly names
NASA as provider, unsupported snowfall is exported as `"none"`. These legacy
limitations require source review before interpreting the data scientifically.

New weather batch v2 records retain provider, units and time basis; unavailable
values stay missing and pre/post aggregates report their valid-day counts.
The NASA fallback keeps corrected total precipitation as `precipitation_sum` in
the internal checkpoint, not as `rain_sum`: it cannot supply separate rain-only
and snowfall measurements. Those fields remain `"none"` in this public schema,
while valid fallback temperature extrema can still be exported. No provider
mixing is used to fill gaps. Open-Meteo days use its reported timezone; NASA
fallback days use explicitly requested local solar time, recorded in the source
checkpoint. The two daily time conventions should not be treated as identical.
See the [Open-Meteo variable definitions](https://open-meteo.com/en/docs/historical-weather-api)
and [NASA POWER daily API](https://power.larc.nasa.gov/docs/services/api/temporal/daily/).

### Satellite

Products are `sentinel_2_rgb`, `sentinel_2_false_color`, `sentinel_2_raw_bands`,
`sentinel_1_sar`, `sentinel_3_thermal`, both sensor validity masks and `worldcover`.
These are generic categories, not inferred maps of rain, clouds or flood damage.
Product lists contain only downloaded files in chronological order. Sensor
availability arrays preserve all 21 days, including missing acquisitions/errors.
Cloud cover is the catalog scene metadata, not a measured cloud percentage for
the final crop. The bbox is the processed AOI, not the disaster footprint.

Raw S2 and S1 files are multiband TIFFs. The false-color band order is recorded
from the manifest. S3 SLSTR thermal data are brightness temperatures in K, **not
derived Land Surface Temperature**. WorldCover is a static raster with a saved
reference year, not daily or necessarily contemporary with the event.

### News, summary and causal chain

`filtered_final_articles` comes from the saved final news engine article list,
deduplicated by URL. This does not assert that all those articles were used by
the later summary or causal filters. Each exported article contains only
`source`, `url`, `relevance_score`, `relevance_reasons`, `relevance_penalties`.
Titles and article bodies are not copied. Source counts refer to this retained
list, not all queried services. Saved search provenance determines global,
regional and fallback categories; DuckDuckGo is a fallback. A source whose
category cannot be reconstructed is retained as an article and reported in the
audit, but is not arbitrarily assigned to a group. Group counts can therefore
sum to less than the total only in these explicitly warned cases.

`summary.total_chars` counts news-context characters, not summary characters.
Only summaries marked `accepted` are exported as text. Other or missing texts
become `"none"`; missing summaries do not invalidate an otherwise eligible
coordinate/chain/image intersection.

Causal `steps` retain `n_event`, normalized `type_event`, `description`, and
`supporting_quote`. Audit counters retain discarded/fuzzy steps, model and
normalizer/prompt versions where saved. This is reuse of the prior validation,
not a new causal inference or independent verification of causal edges.
Quotes remain source excerpts even though article bodies and prompts are removed.
Review source attribution, redistribution terms and quote permissions before
public release; this exporter does not grant a license or upload data.

## Cluster workflow

Run from the repository after the normal Git push/pull, using the existing
environment. No Copernicus credentials or GPU are required for this stage.
Do not export while the source files or satellite manifests are being updated.

First check the full selection without copying or writing anything:

```bash
python src/export_final_event_dataset.py --dry-run
```

If the default weather file is absent or incompatible with the final events,
the following targeted mode checks only coordinates, causal chains and images,
without requiring weather/news/summary input files:

```bash
python src/fetch_weather_batch.py --release-events-only --dry-run
python src/fetch_weather_batch.py --release-events-only --limit 3 --sleep-seconds 3
python -u src/main.py release --execute --steps weather --weather-release-events-only --weather-sleep-seconds 3
```

The first command writes nothing; the second downloads a three-event smoke
test; the third resumes the same checkpoint for the full eligible intersection.
Do not run the second and third simultaneously. Weather files are written to
`results/weather/weather_2014_plus.json` and its progress CSV, not the historical
combined news/weather JSON. The full default pipeline remains unchanged in
scope; this flag is for an existing dataset whose causal/satellite work is done.

`fetched` means all four variables have 21 finite daily values; `partial` means
some values are available and `failed` means none are usable. These are retrieval
coverage states, not claims of independent scientific validation. Same-version
compatible `fetched`/`partial` records are reused; failed records retry on the
next run. Standalone `--retry-partial` retries incomplete series too. A retry
that loses coverage preserves the prior compatible record instead of mixing
providers. A version/date/coordinate change invalidates reuse. Checkpoints use
atomic replacement and a lock; corrupt checkpoints fail visibly rather than
being silently replaced. Internal missing values become `"none"` at final export.

Create a real, automatically selected one-event preview in its own directory:

```bash
python src/main.py release --execute --steps release-package \
  --release-limit 1 --release-output-dir results/release_preview
```

To request a specific eligible event instead, use `--release-event-id ID`.
The exporter does not substitute a different event when the requested id fails
the checks. The limit is applied to eligible events, not to the first input rows.

After inspecting the real preview, create the complete package:

```bash
python -u src/main.py release --execute --steps release-package
```

The `all` and `final` groups include `release-package` automatically. The
existing all-event CSV remains available through `--steps final-dataset`.
`--satellite-all-events true` changes satellite collection, not the public JSON
intersection: public records still need a valid causal chain.

Defaults use the final geocoding CSV, normalized v8 causal CSV, validated v5
summary CSV, complete weather/news JSON and general satellite manifests.
Paths can be overridden through the existing main options or standalone
exporter flags; see `python src/export_final_event_dataset.py --help`.
Missing source files fail explicitly. Use `--allow-missing-context` (standalone)
or `--release-allow-missing-context` (main) only when knowingly publishing absent
weather/news/summary blocks. Individual missing records are audited as warnings.

Copies are byte-verified and originals are never moved, renamed or deleted.
The release requires additional disk space comparable to its selected images.
Repeat the same command to resume an interrupted **identical** export; already
copied files are hash-checked. Changed inputs, selections or incompatible files
require a new output directory. Nothing is silently overwritten or cleaned up.
Do not manually add unrelated images to the managed release folder.
Temporary copies are staged beside the release directory, on the same
filesystem, not inside the public image tree. A hard process termination can
leave `.dataset-export-*` files there; they are not publication assets and are
not automatically deleted or mistaken for completed images on resume.

To transfer the result, keep `data`, `images`, the README and package manifest
together. Only a package with manifest status `complete` should be uploaded
manually. A JSON path is a file reference, not a built-in image viewer.
